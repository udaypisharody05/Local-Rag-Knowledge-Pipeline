# Implementation Plan: Local RAG Knowledge Pipeline (Revised)

This document describes the architectural design, consistency guarantees, data schema, security parameters, and phased implementation roadmap for the **Local RAG Knowledge Pipeline**.

---

## 1. Updated Assumptions & Architectural Decisions

* **Single-Server Simplicity:** To avoid distributed concurrency problems, the MVP is designed for a single server.
  * **Uvicorn is configured with `workers = 1`.**
  * **Celery is configured with ingestion concurrency `concurrency = 1`.**
  This eliminates multi-process write competition on the snapshot files and local databases, guaranteeing sequential, predictable writes and reads.
* **Database as Single Source of Truth:** PostgreSQL is the definitive source of truth. All documents and chunks are permanently stored in Postgres. FAISS and BM25 indexes are ephemeral, derived representations that can be fully rebuilt from the database at any time.
* **Immutable Retrieval Snapshots:** Instead of mutating vector/keyword indexes inline or checking file timestamps (`mtime`), we implement a versioned, immutable snapshot design. An active snapshot is loaded into memory as a single read-only object. When a new snapshot is built by Celery, FastAPI swaps its active pointer atomic-style.
* **No SQLite for Integration Tests:** SQLite lacks support for PostgreSQL JSONB, native UUID types, and specific transaction semantics. We will use a dedicated PostgreSQL Docker container (or distinct database) for integration tests, along with a Redis test instance.
* **Hallucination Mitigation vs. Prevention:** Hallucination cannot be fully "prevented" in LLMs. The system implements **hallucination mitigation** using deterministic citation injection, strict negative prompts (refusal when context is lacking), and automated context relevance checks (insufficient-context logic).

## 2. Consistency Model & Snapshot Lifecycle

### Directory Structure
Indexes are stored under a versioned filesystem hierarchy:
```text
storage/
├── indexes/
│   ├── versions/
│   │   ├── 000001/
│   │   │   ├── faiss.index
│   │   │   ├── faiss_mapping.json
│   │   │   ├── bm25.pkl
│   │   │   └── manifest.json
│   │   └── 000002/
│   └── active_version.txt
```

### Ingestion Snapshot Build Flow (Celery Worker)
1. **Read chunks:** Read all active (non-deleted) chunks from PostgreSQL.
2. **Build FAISS:** Generate local embeddings via Ollama and build a new, clean FAISS index.
3. **Build BM25:** Tokenize text chunks and build a new BM25 index.
4. **Serialize:** Write `faiss.index`, `faiss_mapping.json` (mapping FAISS vector ID to DB chunk UUID), `bm25.pkl` (pickled BM25 model), and `manifest.json` into a new version directory (e.g., `storage/indexes/versions/000002/`).
5. **Validate:** Count validation: verify the vector count in FAISS matches the document count in BM25 and chunk count in PostgreSQL.
6. **Write Manifest:** Write `manifest.json` containing embedding model, chunking configuration hash, version number, chunk count, and creation timestamp.
7. **Atomic Version Swap:** Update `storage/indexes/active_version.txt` with the new version name (e.g. `000002`).
8. **DB Update:** Insert or update `retrieval_index_versions` record in PostgreSQL, marking the version as `ACTIVATED`.

### FastAPI Snapshot Load Flow
* On startup, FastAPI reads `active_version.txt` and loads the corresponding FAISS, BM25, and mapping files into an in-memory `RetrievalSnapshot` object.
* The API exposes a reload endpoint/mechanism. When triggered (or checked periodically), FastAPI acquires an internal `threading.Lock`, reads the new path, deserializes the new files into a new `RetrievalSnapshot` instance, and replaces the active pointer referencing the snapshot.
* Since the pointer swap is atomic in Python, query requests executing concurrently continue reading the old snapshot without interruption until the pointer swaps.

## 3. Database Schema

### `documents`
Stores document metadata and lifecycle states.
* `id`: UUID (Primary Key)
* `source_name`: String (Human-readable name)
* `source_type`: String (`pdf`, `markdown`, `txt`, `repository`, `csv`, `json`)
* `source_identifier`: String (Unique business identifier: e.g., relative repo path, clean filename)
* `original_filename`: String (Unsanitized upload filename)
* `storage_path`: String (Secure path generated by the server inside `storage/documents/`)
* `mime_type`: String
* `size_bytes`: BigInteger
* `content_hash`: String (SHA-256 of the raw file content)
* `status`: String (`PENDING`, `INDEXED`, `FAILED`, `DELETED`)
* `parser_version`: String (Identifier for parsing logic)
* `chunking_config_hash`: String (SHA-256 hash of configuration settings: chunk size, overlap)
* `embedding_model`: String (Name of the model used to index)
* `indexed_at`: DateTime (Nullable)
* `deleted_at`: DateTime (Nullable)
* `created_at`: DateTime
* `updated_at`: DateTime

### `document_chunks`
Stores granular sections of text with structural metadata.
* `id`: UUID (Primary Key)
* `document_id`: UUID (Foreign Key to `documents.id` ON DELETE CASCADE)
* `text_content`: Text
* `chunk_index`: Integer
* `content_hash`: String (SHA-256 of text_content)
* `token_count`: Integer
* `page_number`: Integer (Nullable)
* `section_title`: String (Nullable)
* `repo_relative_path`: String (Nullable)
* `record_id`: String (Nullable)
* `start_offset`: Integer (Nullable)
* `end_offset`: Integer (Nullable)
* `metadata`: JSONB (For extension parameters)
* `created_at`: DateTime
* `updated_at`: DateTime

### `ingestion_jobs`
Tracks Celery worker indexing history and progress.
* `id`: UUID (Primary Key)
* `document_id`: UUID (Foreign Key to `documents.id`, Nullable)
* `celery_task_id`: String (Nullable)
* `job_type`: String (`INDEX`, `REINDEX`, `DELETE`)
* `status`: String (`PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`)
* `source_name`: String
* `progress_current`: Integer (Defaults to 0)
* `progress_total`: Integer (Defaults to 100)
* `attempt_count`: Integer (Defaults to 0)
* `error_message`: Text (Nullable)
* `started_at`: DateTime (Nullable)
* `completed_at`: DateTime (Nullable)
* `created_at`: DateTime
* `updated_at`: DateTime

### `retrieval_index_versions`
Tracks historical and active versions of the retrieval snapshot.
* `id`: UUID (Primary Key)
* `version`: Integer (Unique, e.g. 1, 2, 3...)
* `status`: String (`BUILDING`, `ACTIVATED`, `DEPRECATED`, `FAILED`)
* `chunk_count`: Integer
* `embedding_model`: String
* `chunking_config_hash`: String
* `storage_path`: String (Path to version directory)
* `error_message`: Text (Nullable)
* `created_at`: DateTime
* `activated_at`: DateTime (Nullable)

## 4. Duplicate & Reindex Behavior

Duplicate detection is resolved via the composite of:
`[content_hash, source_identifier, parser_version, chunking_config_hash, embedding_model]`

### MVP Behavior Logic
1. **Identical content uploaded to different source identifiers:**
   Allowed. They represent distinct documents in the knowledge base (e.g. same text file placed in two repository locations).
2. **Identical content uploaded twice to the same source identifier:**
   * **Action:** Reject the upload. Return `409 Conflict` with the existing document ID.
3. **Modified content uploaded to an existing source identifier:**
   * **Action:** Perform an inline re-index. Mark the old document as `DELETED` (with `deleted_at` timestamp), create a new document record, process and extract new chunks, and trigger a Celery job to rebuild the retrieval snapshot. Chunks associated with the deleted version are naturally excluded from the rebuild.
4. **Changed parsing logic, chunking config, or embedding model:**
   Any changes to these parameters invalidates the previous index.
   * **Action:** On system start or configuration reload, check if any active document lacks chunks matching the active parameters. If so, trigger a rebuild task for those documents.

## 5. Secure Storage & Repository Rules

### Path Protection & Absolute Path Restriction
* Clients are forbidden from sending absolute server paths for file uploads. The server writes uploads into `storage/documents/` using UUID-based names to prevent directory traversal attacks (e.g. filename `../../etc/passwd` is sanitized).
* For Repository Ingestion, repositories must be located inside a designated directory: `storage/repositories/`.
* The API accepts a `repository_id` or `directory_name` relative to that root.
* The API verifies the resolved path using `os.path.commonpath` to ensure it lies strictly within the `storage/repositories/` boundary. If it resolves outside, it immediately throws `403 Forbidden`. Symlinks are resolved using `os.path.realpath` before check.

### Repository Exclusions
By default, the following directories, files, and rules apply:
* **Excluded Paths:** `.git/`, `node_modules/`, `.venv/`, `venv/`, `dist/`, `build/`, `__pycache__/`, `coverage/`, `.idea/`, `.vscode/`.
* **Binary Exclusion:** Exclude files with non-text MIME types or signatures.
* **Limits:**
  * Maximum file count: `1000` files per repository.
  * Maximum individual file size: `2 MB`.
  * Maximum total repository size: `50 MB`.
  * Allowed extensions: `.py`, `.js`, `.ts`, `.tsx`, `.html`, `.css`, `.json`, `.md`, `.txt`, `.rs`, `.go`, `.java`, `.cpp`, `.h`, `.cs`, `.sh`.

## 6. CSV & JSON Ingestion Constraints

* **Maximum Upload Size:** `5 MB`.
* **Maximum Records:** `10,000` rows.
* **Maximum Field Length:** `4096` characters. Fields exceeding this are truncated.
* **Supported JSON Shape:** Must be a flat list of JSON objects, or a single dictionary containing an array of flat objects.
* **Nested JSON Flattening:** Nested objects are flattened into dot-notation strings (e.g. `{"user": {"name": "Alice"}}` becomes `{"user.name": "Alice"}`). Arrays of objects are excluded or serialized to strings.
* **Record ID Selection:** Look for common key names: `id`, `uuid`, `record_id`, `index`. If none exist, use the row sequence number.
* **Row-to-Chunk Conversion:** Format the chunk text as a descriptive structured block:
  ```text
  Dataset Row
  Row ID: 452
  Content:
  name: Alice
  user.name: Alice
  role: Administrator
  ```
  All column keys are preserved in the chunk metadata JSON.

## 7. Citations & Grounding

### Citations
Before sending the context to the LLM, the retrieval service assigns distinct labels to chunks:
```text
[SOURCE_1]
Document Name: deployment_guide.pdf
Page Number: 4
Content: ...

[SOURCE_2]
Repository Path: app/main.py
Content: ...
```
The model prompt instructs the LLM: *"When referencing facts, end the sentence with the exact source label, e.g. [SOURCE_1]."*
* **Post-processing:** The API intercepts the generated response. It parses the text for occurrences of `[SOURCE_N]` and maps them back to the verified Postgres chunk record.
* The response output includes the raw `answer` string and a structured array of citations. The LLM is never trusted to write the file path, document ID, or chunk ID itself.

### Insufficient-Context Policy (Hallucination Mitigation)
We check confidence parameters before querying:
1. **Empty Check:** If number of retrieved chunks = 0, abort immediately and return the refusal template.
2. **Similarity Threshold:** If the highest dense cosine similarity score is below `MIN_DENSE_SCORE` (e.g., 0.6) and BM25 score is below `MIN_BM25_SCORE` (e.g. 5.0), skip the LLM entirely.
3. **Refusal Template:** Return a pre-configured static refusal: *"I am sorry, but the provided documentation does not contain enough information to answer this question."* along with an empty citations list.

## 8. API Contract

### `POST /documents/upload`
Uploads a TXT, Markdown, or PDF file.
* **Request:** Multipart form upload (`file`).
* **Response:**
  ```json
  {
    "job_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "document_id": "8fa85f64-5717-4562-b3fc-2c963f66afa7",
    "status": "PENDING"
  }
  ```

### `POST /repositories/index`
* **Request:**
  ```json
  {
    "repository_directory": "my-backend-app",
    "allowed_extensions": [".py", ".md"]
  }
  ```
* **Response:** same job status schema.

### `POST /datasets/upload`
* **Request:** Multipart form upload (`file` CSV or JSON).
* **Response:** same job status schema.

### `POST /query` (Non-streaming)
* **Request:**
  ```json
  {
    "query": "How do I deploy on port 8000?",
    "dense_k": 5,
    "sparse_k": 5,
    "rerank_k": 3
  }
  ```
* **Response:**
  ```json
  {
    "answer": "To deploy on port 8000, modify the docker-compose ports mapping [SOURCE_1].",
    "citations": [
      {
        "source_id": "SOURCE_1",
        "document_id": "8fa85f64-5717-4562-b3fc-2c963f66afa7",
        "chunk_id": "2fa85f64-5717-4562-b3fc-2c963f66afa8",
        "source_name": "docker-compose.yml",
        "page_number": null,
        "section_title": null,
        "repo_relative_path": "docker-compose.yml"
      }
    ],
    "retrieval": {
      "snapshot_version": 2,
      "retrieved_chunk_ids": ["2fa85f64-5717-4562-b3fc-2c963f66afa8"]
    }
  }
  ```

### `POST /query/stream`
* **Request:** same as `/query`.
* **Response:** `text/event-stream` returning Server-Sent Events (SSE):
  * Event: `token` -> `{"text": "To"}`
  * Event: `token` -> `{"text": " deploy"}`
  * ...
  * Event: `citations` -> `{"citations": [...], "snapshot_version": 2}`

### `GET /jobs/{job_id}`
* **Response:**
  ```json
  {
    "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "status": "PROCESSING",
    "progress_current": 30,
    "progress_total": 100,
    "error_message": null
  }
  ```

## 10. Revised Phase Roadmap & Acceptance Criteria

### Phase 1: Foundation
* **Tasks:** Set up FastAPI, config system, PostgreSQL, Alembic migrations, health/readiness endpoints, API-key authentication, Docker Compose with Postgres.
* **Acceptance Criteria:**
  - `GET /health` and `GET /ready` return `200 OK`.
  - Database migrations apply correctly on start.
  - Sending requests without API key returns `401 Unauthorized`.
  - Database schema tests verify creation of all 4 models.

### Phase 2: Synchronous Ingestion
* **Tasks:** Implement file validation, storage path protection, and parsing for TXT, Markdown, and PDF. Implement recursive chunking and duplicate check logic.
* **Acceptance Criteria:**
  - Upload of `pdf` is successfully stored under UUID path, parsed, chunked, and saved in Postgres database synchronously.
  - Double upload of identical content to the same identifier returns `409 Conflict`.
  - Uploading file with `../` path throws error or is safely sanitized to flat UUID.

### Phase 3: Dense Retrieval
* **Tasks:** Integrate local embedding calls via Ollama. Build FAISS index creation flow. Write FAISS and mappings file structure.
* **Acceptance Criteria:**
  - Embeddings are generated successfully.
  - Snapshot directory is written with `faiss.index` and `faiss_mapping.json`.
  - Calling dense search returns correct document UUIDs from mapping.
  - Snapshot can be reloaded in memory thread-safely.

### Phase 4: Sparse & Hybrid Retrieval
* **Tasks:** Implement BM25 index generation, persist `bm25.pkl` inside snapshot directory, write RRF fusion to merge FAISS and BM25 scores.
* **Acceptance Criteria:**
  - Hybrid retrieval queries successfully combine BM25 keyword matches and FAISS dense semantic matches.
  - RRF outputs are deterministic.
  - Index versions contain both `faiss.index` and `bm25.pkl`.

### Phase 5: Non-Streaming Grounded Generation
* **Tasks:** Integrate Ollama LLM client. Write context prompts, insufficient-context checks, and citation metadata parsing.
* **Acceptance Criteria:**
  - `/query` returns grounded answers using context.
  - Answer contains citation tokens (`[SOURCE_1]`), mapped to structured citation list.
  - If query has no relevant context, LLM is bypassed and static refusal returned.

### Phase 6: Streaming
* **Tasks:** Implement SSE streaming query endpoint `/query/stream` using asynchronous generator, with citation metadata appended at the end of the stream.
* **Acceptance Criteria:**
  - Calling stream returns tokens using standard SSE protocol (`event: token`).
  - Closing client connection triggers clean worker cleanup.
  - Final message delivers citations list.

### Phase 7: Asynchronous Ingestion
* **Tasks:** Integrate Redis and Celery. Set Celery concurrency to 1. Move ingestion logic to celery task. Track progress in `ingestion_jobs`.
* **Acceptance Criteria:**
  - File upload returns a `job_id` immediately with `PENDING` state.
  - Celery processes task, progress is tracked, and changes job state to `COMPLETED`.
  - New snapshot directory is created and activated *only* on successful generation.
  - If parsing fails, job state changes to `FAILED` and error is saved.

### Phase 8: Deletion & Reindexing
* **Tasks:** Implement document delete and re-index endpoints. Delete triggers a full rebuild of the retrieval snapshot.
* **Acceptance Criteria:**
  - Deleting a document removes its storage file, changes DB status to `DELETED`, and triggers background snapshot rebuild.
  - Post-delete queries do not return deleted chunks.
  - Re-indexing rebuilds snapshot, cleaning stale index files.

### Phase 9: Advanced Ingestion
* **Tasks:** Implement Repository scanning and structured CSV/JSON data parsers with size and format limits.
* **Acceptance Criteria:**
  - Repository scan only reads configured extensions, respects limits (files/size), resolves symlinks safely.
  - CSV files map row indices to chunk record IDs.
  - JSON objects flatten correctly.

### Phase 10: Reranking & Evaluation
* **Tasks:** Define Reranker interface. Implement FlashRank. Create `evaluate.py` testing hybrid combinations vs baselines.
* **Acceptance Criteria:**
  - FlashRank successfully re-orders retrieved chunks.
  - Evaluation script runs and outputs comparison report including MRR, Recall@K, and peak memory metrics.

### Phase 11: Hardening & Deployment
* **Tasks:** Add request rate-limiting, upload body limits, structured logger, database backup script, deployment documentation.
* **Acceptance Criteria:**
  - Exceeding file limits throws `413 Payload Too Large`.
  - Exceeding rate limit throws `429 Too Many Requests`.
  - Complete backup and restore script runs successfully.

## 11. Testing & Evaluation Strategy

### Testing Strategy
* **Unit Tests:** Pytest fixtures test chunking logic, text extraction, path validation, and RRF calculations.
* **Database Integration Tests:** Run within a dedicated PostgreSQL container to verify migrations, constraints, and cascading deletes.
* **Celery Integration Tests:** Test lock behavior and failed job recovery with a live Redis instance.
* **Ollama Mocking:** Mocks HTTP responses for Ollama embedding and LLM endpoints to allow offline, deterministic test executions.

### Evaluation Strategy
* **Dataset:** `evaluation/dataset.json` contains a validation set of 50 sample questions, expected ground-truth documents/chunks, and answerable labels.
* **Metrics Tracked:**
  - **Retrieval Metrics:** Recall@3, Recall@5, MRR, Precision@3.
  - **System Metrics:** Time-to-First-Token (TTFT), Peak RAM, Index sizes, Ingestion items/sec.
  - **Grounding Metrics:** Citation coverage (percentage of claims backed by verified sources), Refusal Accuracy (correct refusal on unanswerable questions).

## 12. Known Limitations & Future Improvements

1. **Rebuild Overhead:** Rebuilding the entire index snapshot on every ingestion, deletion, or re-indexing is computationally expensive for millions of chunks. *Future Optimization:* Incremental FAISS appending and partial BM25 updates.
2. **Resource Constraints:** Heavy CPU load during FlashRank reranking or embedding computations on systems without GPU pass-through.
3. **No Multi-Tenancy:** The application is built for single-user/internal intranet security. Expanding to multi-tenant operations will require Row-Level Security (RLS) in PostgreSQL and separate vector indexes or metadata filters in FAISS.
